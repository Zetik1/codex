## 1. Что это

Веб-сервис, где любой человек собирает собственную базу знаний из готовых блоков,
настраивая их под себя.

Не текстовый редактор и не файловая свалка. Статья здесь — не сплошной текст,
а **набор блоков**: заголовок, абзац, галерея, таблица характеристик, схема, врезка
с видео, список ссылок. Пользователь берёт готовый блок, наполняет содержимым
и настраивает оформление. Если готового не хватает — берёт пустой блок и собирает свой.

Ключевая ценность: структура данных задаётся пользователем, а не разработчиком.
Один заводит библиотеку по своей вселенной, другой — гайды по игре, третий —
техническую документацию. Кода при этом не меняется ни строки.

## 2. Модель использования

**Мультиарендный сервис.** Один запущенный экземпляр приложения обслуживает всех
пользователей сразу. Каждый заводит свою библиотеку — изолированное пространство
со своими типами статей, своими полями, своим оформлением. Данные библиотек
не пересекаются и не видят друг друга.

Аналогия, которой это описал друг Влада, — «предоставляю мощности с готовым сервисом,
человек приходит в песочницу и делает что хочет». Это точное описание модели SaaS —
но именно **модели**, а не того, что мы строим.

Формулировка, которой стоит описывать проект вслух и в README:

> Учебный мультиарендный каркас базы знаний с изоляцией арендаторов
> и безопасными плагинами внутри своей библиотеки.

Слова «платформа», «маркетплейс», «SaaS-сервис» из описания убраны сознательно:
проект их не выполняет, а обещание, которое не выполнено, на собеседовании
работает против тебя. Полный список того, чего здесь нет, — раздел 4, Out of Scope.

**Что это значит технически.** У каждой строки почти в каждой таблице есть
`library_id`. Любой запрос к базе обязан фильтроваться по нему. Забыл фильтр —
один пользователь видит чужие данные. Это не абстрактная угроза, а самая частая
уязвимость в мультиарендных приложениях, и она проверяется тестами с первого дня.

**Про хостинг.** Разработка целиком локальная, 0 ₽. Вопрос реальных «мощностей»
(сервер, домен, оплата) встаёт только при публичном запуске и в этот план не входит.
Приложение при этом сразу пишется так, чтобы разворачиваться одной командой.

## 3. Ядро идеи: блоки

Это главное отличие от вики-движков и то, вокруг чего строится вся модель данных.

### Как устроена статья

У статьи две части: **поля** — короткие значения по схеме её типа, и **блоки** —
упорядоченный список содержимого. Каждый блок знает свой тип и хранит свои данные:

```
Статья «Врай»
├── тип    → «Раса»                                    ← ArticleType этой библиотеки
├── поля   → { "level": "низшая", "power": 3, "is_dead": false }   ← по схеме типа «Раса»
└── блоки  → упорядоченный список:
    ├── «Заголовок» → { "text": "Врай", "level": 1 }
    ├── «Инфобокс»  → { "show": ["level", "power"] }   ← что показать; значения берёт из полей
    ├── «Текст»     → { "html": "<p>Раса, возникшая из <a ...>облака аспектов</a></p>" }
    ├── «Галерея»   → { "images": [{ "src": "...", "caption": "..." }] }
    └── «Связи»     → { "relations": [{ "kind": "враждует", "target": "Вечные" }] }
```

Порядок блоков, их набор и содержимое — целиком на пользователе.

### Типы статей и поля

Это то место, где «структура задаётся пользователем» превращается из лозунга
в работающий механизм. Разбираем отдельно, потому что здесь проще всего ошибиться.

**Тип статьи** — сущность, которую пользователь заводит сам внутри своей библиотеки:
«Раса», «Персонаж», «Оружие», «Локация». У типа есть **схема полей**: какие поля
бывают у статей этого типа, как они называются и что в них можно класть.

```
ArticleType
├── library_id
├── slug          "race"
├── name          "Раса"
└── fields_schema [
      { "key": "level",  "label": "Уровень", "type": "select", "options": [...] },
      { "key": "power",  "label": "Сила",    "type": "number" },
      { "key": "is_dead","label": "Погибла", "type": "bool" }
    ]
```

Значения лежат в самой статье, в отдельном поле `fields`, плоским словарём
по этим ключам: `{ "level": "низшая", "power": 12 }`.

**Главное правило: поля — свойство статьи, а не содержимое блока.**
Блок «Инфобокс» их только *рисует* — берёт значения из `fields`, подписи из
`fields_schema` и выводит карточку. Сам он ничего не хранит.

Почему именно так, а не «пусть пользователь набьёт поля прямо в инфобоксе»:

- **У полей появляются стабильные ключи.** Иначе у двух статей одного типа
  «сила» окажется записана как «Сила», «сила» и «СИЛА» в трёх разных блоках,
  и сослаться на неё снаружи невозможно.
- **Плагину есть на что ссылаться.** Манифест просит `fields: [power, armor]` —
  это ключи из схемы типа. Сервер сверяет запрос со схемой и отдаёт только объявленное.
  Без схемы манифест ссылается в пустоту.
- **Поиск и фильтры становятся возможными:** «всё оружие с уроном больше 10».
  По значениям, размазанным внутри блоков, такой запрос не построить.
- **Валидация.** `type: number` в схеме — и Pydantic не пустит туда текст.

Ответ на вопрос, который на собеседовании задают первым:
*«Откуда манифест плагина знает, что такое "сила"?»* — ключ `power` объявлен
в `fields_schema` типа «Раса» в этой библиотеке; эндпоинт выдачи данных сверяет
манифест с этой схемой.

#### Допустимые типы полей в версии 1

Ровно пять, список закрытый: **`string`, `number`, `bool`, `date`, `select`**
(последний — с перечнем допустимых значений).

`date` хранится и передаётся строкой в формате **ISO 8601, `YYYY-MM-DD`**, без времени
и без часового пояса. Это зафиксировано здесь, а не оставлено «на потом»: иначе
на задаче 0.8 придётся разбирать «05.08.2026», «5 августа» и `2026-08-05T00:00:00Z`
как одно и то же, а на этапе 4 сортировка по дате перестанет работать.

**Ссылочного типа (`ref` на другую статью) в версии 1 нет** — и это не забывчивость.
Связи между статьями в проекте уже есть, и делает их отдельный механизм: модель
`Link` и блок «Связи». Ссылка, спрятанная внутрь поля, породила бы второй способ
делать то же самое — со своим разрешением ссылок, битыми ссылками, каскадным
удалением и своим интерфейсом выбора. Один механизм связей на проект, а не два.

#### Схема тоже проверяется

`fields_schema` пишет пользователь, а значит она такой же недоверенный ввод,
как всё остальное. Динамическое построение модели по чужому описанию без проверок —
это способ уронить сервис, а не гибкость. Правила:

| Ограничение | Зачем |
|---|---|
| `type` только из закрытого списка выше | иначе в схему приедет что угодно, и валидатор сломается на построении |
| `key` подходит под `^[a-z][a-z0-9_]*$`, длина до 40 | ключ попадёт в JSON, в URL, в индекс базы и в манифест плагина. Кириллица, пробелы и точки ломают всё перечисленное |
| ключи внутри типа уникальны | два поля `power` — неразрешимая неоднозначность |
| не больше ~50 полей на тип | иначе один тип с тысячей полей кладёт и валидацию, и индексы |
| `label` до 100 символов, `options` до ~100 значений | те же соображения |

Это не паранойя, а обычная валидация недоверенного ввода — просто вводом здесь
оказывается **описание структуры**, а не сами данные.

#### Как схема меняется со временем

Пользователь заведёт тип, а через месяц захочет его поправить. Изменение схемы,
под которой уже лежат данные, — это миграция, и она умеет быть очень дорогой.
Поэтому в версии 1 правила жёсткие:

| Операция | Версия 1 |
|---|---|
| **Добавить поле** | Можно всегда. У старых статей его просто нет — читается как пустое |
| **Удалить поле** | Можно, если ни у одной статьи в нём нет значения. Иначе — только с явным подтверждением «значения будут удалены», с показом количества затронутых статей |
| **Переименовать ключ** | **Нельзя.** Ключ — это стабильный контракт: на него ссылаются манифесты плагинов и сохранённые фильтры. Хочешь другое название — меняй `label`, он на то и нужен |
| **Сменить тип значения** | **Нельзя.** Удали поле и заведи новое |

Без этих правил задача «интерфейс типов статей» превращается в отдельный продукт
про миграции данных: переименования с обновлением ссылок, приведение типов,
откат неудачной конвертации. Разумно — но не в учебном проекте и не за 18 часов.

### Три уровня свободы

Три уровня — это про **блоки**, то есть про то, что пользователь собирает мышкой,
без единой строчки кода:

| Уровень | Что это | Кто задаёт |
|---|---|---|
| **Готовые блоки** | текст, заголовок, картинка, галерея, таблица, видео, инфобокс, цитата, список ссылок | платформа |
| **Настройка блока** | отступы, цвета, границы, выравнивание, ширина — из набора допустимых значений | пользователь через интерфейс |
| **Пустой блок** | заготовка без формата, собирается из примитивов через интерфейс | пользователь |

**Плагин стоит не в этом ряду.** Это не четвёртый уровень блока, а другая ось:
единственное место в проекте, где появляется исполняемый код пользователя,
со своей моделью угроз, своей изоляцией и своим жизненным циклом. Смешивать их
в одной таблице неправильно — у них не совпадает ни риск, ни способ реализации.

### Плагины: код пользователя

Плагин — это **настоящий код**, который написал пользователь и который платформа
исполняет. Не конструктор из готовых кусков, а свобода написать логику: калькулятор
урона, генератор случайной таблицы, интерактивная карта, пересчёт характеристик
по формуле, сводка по десяткам статей.

Это самая сложная часть проекта и самая ценная. Ценная по двум причинам: она
поднимает сервис на уровень выше обычной вики, и она же — единственная часть,
о которой на собеседовании можно говорить полчаса.

Ограничения и изоляция здесь не «на всякий случай», а условие, при котором фича
вообще имеет право существовать. Ниже — как это устроено.

#### Где исполняется код

Ключевое решение: **код исполняется в браузере посетителя, а не на сервере.**

| Способ | Что происходит | Вердикт |
|---|---|---|
| `exec()` в процессе приложения | код пользователя работает с правами сервера: читает базу, файлы, переменные окружения | **никогда.** Это удалённое исполнение кода, то есть отданный сервер |
| Фильтрация опасных конструкций (RestrictedPython) | «запретим `import os` и `eval`» | **не защита.** Обходов известно много: через интроспекцию объектов добираются до чего угодно. Выглядит как граница, границей не является |
| Контейнер на каждый запуск | Docker без сети, только чтение, лимиты процессора, памяти и времени | **работает,** но дорого: медленный запуск, сложная эксплуатация, ошибка в настройке = чужой сервер |
| **Pyodide в браузере** | CPython, скомпилированный в WebAssembly, исполняется у посетителя | **выбираем это** |

Почему Pyodide подходит:

- **Сервер вне игры.** Плагину физически нечего атаковать: он в песочнице браузера,
  до базы и файловой системы сервера не достаёт.
- **Радиус поражения — одна вкладка одного человека.** Не платформа, не другие
  пользователи, не данные.
- **Ничего не стоит.** Считает процессор посетителя. При росте числа пользователей
  расходы на исполнение плагинов остаются нулевыми — при серверном варианте они
  растут линейно.
- **Требований к железу нет.** Важно: у тебя ноутбук и ПК ниже среднего.
- **Это Python.** Пользователь пишет на том же языке, что и весь проект.

Ограничение честно: браузерный плагин работает с данными, которые ему выдали,
и не может обойти всю библиотеку по расписанию. Если такой сценарий понадобится —
это **отдельное решение** про серверное исполнение в контейнере, отдельная запись
в журнал и отдельный этап. По умолчанию — браузер.

#### Что плагину можно, а что нельзя

Права запрашиваются заранее в манифесте — плагин объявляет, что ему нужно,
и получает только это. Не объявил — не получил.

```
manifest:
  name: Калькулятор урона
  mount: tab              # вкладка у статьи | врезка в статью
  needs:
    - fields: [power, armor]       # ключи из fields_schema типа статьи
    - articles: type=weapon        # выборка статей одного типа
  network: none                    # по умолчанию наружу не ходит
```

Ключи в `needs.fields` — не произвольные слова, а ссылки на схему полей типа статьи
(раздел «Типы статей и поля» выше). Эндпоинт выдачи данных сверяет манифест с этой
схемой: попросил поле, которого в схеме нет, — получил отказ, а не пустое значение.

| Разрешено | Запрещено |
|---|---|
| получить объявленные поля текущей статьи | читать статьи, которые не объявлены в манифесте |
| получить выборку статей объявленного типа | обращаться к чужим библиотекам |
| считать, преобразовывать, генерировать | читать cookie и данные сессии посетителя |
| вернуть статус и метрики наружу | отдавать разметку родительской странице |
| нарисовать результат внутри своего iframe | лезть в страницу платформы вокруг себя |
| — | ходить в сеть (без явного разрешения и белого списка) |

#### Ограничения по ресурсам — что на самом деле работает

Здесь важно не обманывать себя, потому что на собеседовании разница видна сразу.

| Механизм | Насколько надёжен |
|---|---|
| **Таймаут + `worker.terminate()`** | **Жёстко.** Зациклился — поток убит принудительно. Это главная и настоящая граница |
| **Отдельный поток (Web Worker)** | **Жёстко.** Плагин не может подвесить вкладку: интерфейс живёт в основном потоке |
| Размер линейной памяти WebAssembly | **Мягко.** Задаётся сверху при создании, но при выходе за предел Wasm падает с `abort`, а не отдаёт аккуратный `MemoryError`. Ограничение есть, но грязное |
| Жёсткая квота памяти как в контейнере | **Не существует.** Браузер не даёт ограничить память воркера по-настоящему (`--memory` из Docker аналога не имеет) |

Формулировка, которую стоит запомнить: *жёсткий таймаут и принудительное завершение
воркера; память ограничена сверху размером линейной памяти Wasm, но это не квота
уровня контейнера.* Говорить «лимит памяти» как про гарантию — неправда,
и это сразу слышно.

#### Запрет сети — почему `network: none` недостаточно

Строка `network: none` в манифесте — это **декларация намерения**, а не запрет.
У Pyodide нет сокетов, но есть мост в JavaScript (`pyfetch`, модуль `js`),
и через него плагин ходит в сеть браузером в обход любых наших проверок кода.

Настоящий запрет ставится заголовком Content-Security-Policy на странице-песочнице.
Отправная точка выглядит примерно так:

```
Content-Security-Policy:
  default-src 'none';
  script-src  'self' 'wasm-unsafe-eval';
  worker-src  'self' blob:;
  connect-src 'self';
  img-src     'self' data: blob:;
  style-src   'self' 'unsafe-inline';
```

**Почему `connect-src 'self'`, а не `'none'`.** Первая версия этого документа
предлагала `'none'` — красиво, но неработоспособно: Pyodide подтягивает
собственный рантайм (`pyodide.asm.wasm`, архив стандартной библиотеки, колёса
пакетов) обычным `fetch`. С `connect-src 'none'` не запустится сам интерпретатор.

`'self'` означает «только с источника песочницы». А на этом источнике не лежит
ничего, кроме файлов самого Pyodide: ни API, ни данных, ни сессии. То есть
плагин может дотянуться ровно до собственного рантайма — и никуда больше.
Внешние домены отрезаны так же жёстко, как при `'none'`.

Остальные директивы тоже не украшение: `worker-src blob:` нужен, потому что
воркер создаётся из blob-URL; `style-src 'unsafe-inline'` — потому что плагин
возвращает разметку со своим оформлением. Это **отправная точка, а не готовый
для копирования ответ**: точный набор директив добивается на задаче 6.5 по факту,
глядя в консоль браузера. Принцип — «запрещено всё, разрешаем по одной директиве
под конкретную нужду» — важнее, чем конкретные строки.

Разница принципиальная: проверка кода на запрещённые конструкции обходится,
политика браузера — нет. Это тот же принцип, что и с `exec()` против песочницы.

#### Изоляция отображения

Результат плагина показывается в `<iframe sandbox>` **с отдельного источника** —
не вклеивается в страницу статьи.

Причина конкретная: если вставить возвращённую плагином разметку прямо в страницу,
код плагина оказывается в одном источнике с платформой и получает доступ к cookie
и сессии посетителя. То есть плагин крадёт аккаунт любого, кто открыл статью.
Отдельный источник это отрезает: браузер сам не пускает такой iframe к данным
родительской страницы.

Отдельный источник нужен **с первого рабочего плагина**, а не при развёртывании.
Локально это `http://sandbox.localhost:8000` — то же самое приложение, различаемое
по заголовку `Host`. Другой хост означает другой источник, и браузеру этого достаточно;
Docker и настоящий домен для этого не нужны.

Запасной вариант, если `*.localhost` капризничает (на части систем и корпоративных
DNS он резолвится не всегда): **поднять песочницу на втором порту**. Источник —
это схема, хост **и порт**, поэтому `localhost:8000` и `localhost:8001` для браузера
уже разные источники. Третий вариант — прописать имя в файл `hosts`
(`C:\Windows\System32\drivers\etc\hosts`). Любой из трёх годится, важно только,
чтобы источник отличался.

#### Как данные попадают в песочницу

Это тот самый стык, о который разбивается большинство таких схем, и его надо
зафиксировать до начала работы, а не выяснять на шестом этапе.

**Проблема.** Песочница живёт на другом источнике. Значит cookie сессии туда
не поедут (`SameSite=Lax` их не отправит, и это правильно — ровно от этого
мы и защищаемся). Значит iframe **не может сам сходить в API** за данными:
он не аутентифицирован. А с `connect-src 'self'` он ещё и физически не может
обратиться к основному источнику.

**Контракт (решение принято, версия 1):**

```
основная страница                        песочница (другой источник)
─────────────────                        ───────────────────────────
1. читает манифест плагина
2. идёт в API со своей cookie
   GET /api/plugins/{id}/data
3. получает только то,
   что объявлено в манифесте
4. postMessage(данные) ──────────────►  5. Pyodide считает
                                        6. РИСУЕТ РЕЗУЛЬТАТ У СЕБЯ
                                           внутри iframe
8. пишет строку в журнал  ◄──────────── 7. postMessage(статус: ok/ошибка,
   и, если надо, меняет                    время работы, размер вывода)
   высоту iframe
```

**Данные в песочницу попадают только через `postMessage` от родительской страницы.
Песочница ни в какой API не ходит и никаких токенов не имеет.**

#### Правило, без которого вся изоляция бессмысленна

Разметку, которую вернул плагин, **рисует сам iframe и только он**.

| Кто | Что делает |
|---|---|
| Песочница | считает, формирует разметку и **сама её отображает** внутри своего документа |
| Наружу через `postMessage` | уходит **только телеметрия**: статус (успех / ошибка / прерван по таймауту), время работы, при необходимости желаемая высота окна. Разметка и HTML — никогда |
| Основная страница | получает телеметрию, пишет строку в журнал, при необходимости меняет высоту `<iframe>`. **Никакого `innerHTML` с содержимым от плагина** |

Если родитель вклеивает вернувшийся HTML в свою страницу, вся конструкция
схлопывается в ноль: код плагина оказывается в источнике платформы и получает
доступ к cookie и сессии посетителя. То есть ровно та атака, от которой мы
защищались отдельным источником, происходит — просто нашими руками, добровольно.

Формулировка для собеседования: *«результат не пересекает границу источника —
пересекает только статус исполнения»*.

#### Проверка источника у сообщений

`postMessage` сам по себе ничего не защищает: сообщение может прислать любое окно,
а неаккуратно отправленное — прочитать любой получатель. Поэтому с обеих сторон:

- **На приёме** — сверять `event.origin` с ожидаемым источником и молча отбрасывать
  всё остальное. Родитель принимает только от источника песочницы, песочница —
  только от источника платформы.
- **На отправке** — указывать конкретный `targetOrigin`. Не `"*"`: со звёздочкой
  сообщение уедет куда угодно, если окно вдруг сменило адрес.
- Дополнительно сверять `event.source` с тем окном, которому реально отправляли.

Это первое, что спрашивают сразу после CSP, и то, что чаще всего забывают
в чужих примерах из интернета.

#### На источнике песочницы не должно быть API

Логика `connect-src 'self'` держится ровно на одном допущении: на источнике
песочницы нет ничего интересного. Это допущение надо обеспечить явно, а не
надеяться на него.

Маршрутизация по заголовку `Host`: запрос, пришедший на хост песочницы, отдаёт
**только статику** — страницу песочницы, файлы Pyodide, её скрипт. Никаких
`/api`, никаких сессий, никаких шаблонов приложения. То же самое на этапе 8
в конфигурации развёртывания.

Без этого правила `'self'` внезапно означает «весь API приложения», и запрет
сети превращается в его противоположность.

Что даёт контракт в целом:

- Аутентификация остаётся там, где ей место, — на основном источнике, с cookie.
- Плагин получает ровно то, что ему передали. Не «попросил и ему отказали»,
  а «взять больше физически неоткуда».
- Не нужны ни CORS, ни выдача токенов в недоверенный контекст, ни короткоживущие
  тикеты, которые пришлось бы отзывать и проверять.

Проверка полномочий по манифесту при этом никуда не девается — она просто
происходит на шаге 2–3, на сервере, при обычном сессионном запросе.

Альтернатива, которую **не** выбираем: выдавать в iframe одноразовый тикет,
чтобы он сам сходил за данными. Это работает, но требует ослабить `connect-src`,
завести выдачу и отзыв тикетов и объяснять, почему токен в недоверенном контексте
безопасен. Больше движущихся частей ради возможности, которая в этом проекте
не нужна. Записано здесь, чтобы на собеседовании ответить «рассматривали, отказались,
вот почему», а не «не подумали».

#### Жизненный цикл плагина

Плагин живёт и работает **внутри библиотеки своего автора**. Публикация в чужие
библиотеки в этот проект не входит — см. раздел 4 «Границы».

```
черновик  ⇄  рабочий  ⇄  выключен
   │            │            │
только автор  вся своя   код есть,
              библиотека  не запускается
```

- **Черновик** — виден только автору, запускается только у него.
  Пишет ерунду — ломает себе, его право.
- **Рабочий** — включён в своей библиотеке, работает у всех, кто эту библиотеку
  открывает: у автора, редакторов, читателей.
- **Выключен** — снят одним переключателем. Код остаётся, исполнение прекращается.
- Каждый запуск логируется: кто, где, что вернул, сколько работал.

Автоматические проверки кода (запрещённые конструкции, «а нет ли тут `import os`»)
в этот список не входят намеренно. Они обходятся, дают ложное чувство защищённости
и съедают время, которое лучше потратить на песочницу. Защита — это браузер,
отдельный источник и CSP; проверки кода защитой не являются.

#### Что это даёт тебе как специалисту

Это прямое пересечение с твоей специальностью по информационной безопасности:
модель угроз, разграничение прав по манифесту, принцип минимальных полномочий,
изоляция источников, жёсткое ограничение времени исполнения, RCE и почему его
нельзя допускать.
В портфолио джуна такого не бывает почти никогда.

Слово «квоты» в этом перечислении сознательно не используется: квота — это
гарантия уровня ядра или контейнера, а в браузере её нет. Разницу между
ограничением и квотой на собеседовании слышно сразу.

### Закрытый вопрос: сырой CSS

Даём ли редактор сырого CSS для оформления блоков. Решение — **нет**,
только настройки из допустимого набора. Причина: пользовательский CSS протекает
на соседние блоки и ломает вёрстку всей страницы. Заметь, что к плагинам это
не относится — они и так изолированы в отдельном iframe и внутри себя вольны
оформлять что угодно.

## 4. Границы: чего сервис не делает

- **Не хостинг видео.** Видео вставляется ссылкой на внешний сервис.
- **Не соцсеть.** Обсуждения привязаны к статьям, ленты и подписок нет.
- **Не исполняет пользовательский код на сервере.** Плагины считаются в браузере
  посетителя (раздел 3). Серверное исполнение — только как отдельное решение,
  если появится сценарий, который браузером не закрыть.
- **Не редактор офисного типа.** Блоки и поля, а не бесконечная свобода вёрстки.
- **Не содержит ИИ** ни в рантайме, ни при сборке.
- **Не готовится к продакшену с живыми пользователями.** Цель — работающий
  инструмент и портфолио, а не бизнес.

### Вне рамок проекта (Out of Scope)

Отдельно от предыдущего списка. Там — чем сервис не является по замыслу.
Здесь — то, что в замысел укладывается, но сознательно не делается.

- **Маркетплейс плагинов.** Публикация плагина в чужие библиотеки, каталог,
  очередь модерации, роль модератора платформы, отзыв опубликованного, репутация
  авторов. Это **второй продукт**, спрятанный внутри первого: он требует админки,
  интерфейса проверки, аудита и ручного труда, который не масштабируется.
  Плагины версии 1 работают только в библиотеке своего автора.
- **История правок и откат версий.** Полезно, но это отдельная модель данных,
  сравнение версий и интерфейс к ним.
- **Одновременное редактирование.** Двое в одной статье — конфликты правок,
  блокировки или CRDT. Отдельная большая тема, в проект не входит.
- **Резервное копирование и восстановление данных.** Нужно сервису с живыми
  пользователями, а его здесь нет.

**Как это звучит в одну строку** (например, в README или на собеседовании):
учебный мультиарендный каркас базы знаний с изоляцией арендаторов и безопасными
плагинами внутри своей библиотеки. Не «SaaS-платформа с маркетплейсом» — обещание,
которого проект не выполняет, работает против тебя, а не на тебя.

## 5. Структура проекта

Приложение делится на слои. Каждый слой знает только про соседний снизу —
это не бюрократия, а способ менять одно, не ломая другое.

```
codex/
├── app/
│   ├── models/        SQLAlchemy: описание таблиц базы
│   ├── schemas/       Pydantic: проверка входящих и исходящих данных
│   ├── services/      бизнес-логика: «создать статью», «найти», «связать»
│   ├── routers/       HTTP-эндпоинты FastAPI
│   ├── blocks/        типы блоков: описание, валидация, рендер
│   ├── plugins/       манифесты, выдача данных плагину, статусы
│   ├── templates/     Jinja2: HTML-страницы
│   ├── static/        CSS, JS, редактор блоков
│   │   └── sandbox/   страница-песочница: Pyodide, воркер, запуск плагина
│   ├── db.py          подключение к базе
│   └── main.py        точка входа
├── media/             загруженные файлы, разложенные по library_id
├── migrations/        Alembic: версии схемы базы
├── tests/             pytest
├── docs/              BRIEF.md, ROADMAP.md, решения
└── docker-compose.yml
```

**Почему слои именно такие.** Логика «создать статью» лежит в `services/`, а не
в обработчике HTTP. Поэтому её можно вызвать из скрипта, из теста, из консоли —
и позже из другого интерфейса, не переписывая. Обработчик в `routers/` занимается
только HTTP: разобрать запрос, позвать сервис, вернуть ответ.

Это заметно скучнее, чем свалить всё в один файл, и на маленьком проекте выглядит
избыточным. Но именно так устроены рабочие проекты, и на собеседовании спросят
про это, а не про умение писать циклы.

## 6. Технологии

Ты просил решать по потребностям проекта, а не по вкусу. Ниже — что выбрано и почему.

### Сразу поправка по терминам

Друг сказал «постгрес для статей, алхими для пользователей». Это смешение
двух разных вещей, и в таком виде на собеседовании прозвучит плохо.

- **PostgreSQL** — это база данных. Программа, которая хранит данные на диске.
- **SQLAlchemy** — это ORM, библиотека Python, которая с базой разговаривает.

Они не альтернативы друг другу и не делят между собой данные. Это два этажа
одной конструкции: **и** статьи, **и** пользователи лежат в PostgreSQL,
и к **и** тем, **и** другим обращаемся через SQLAlchemy.

### Ядро

| Технология | Роль | Почему она |
|---|---|---|
| **Python 3.14** | язык | уже установлен, цель обучения |
| **SQLAlchemy 2.0** | ORM — работа с базой через объекты Python | стандарт для Python-бэкенда вне Django; версия 2.0 обязательна, синтаксис 1.x устарел |
| **Alembic** | миграции — версионирование структуры базы | без него любое изменение схемы означает удалить базу и потерять данные |
| **Pydantic v2** | валидация данных на входе и выходе | блоки приходят как JSON произвольной формы — без валидации в базу попадёт мусор |
| **SQLite → PostgreSQL** | база данных | детали ниже |
| **FastAPI** | веб-фреймворк, HTTP-слой | приоритет по совету друга-тимлида; даёт автодокументацию из типов |
| **Jinja2 + HTMX** | серверный рендеринг страниц | интерфейс без React: страницы собираются на сервере, HTMX обновляет куски без перезагрузки |
| **Editor.js** | редактор блоков в браузере | блочная модель совпадает с нашей один в один, отдаёт готовый JSON, обычная JS-библиотека без фреймворка |
| **Pyodide** | CPython в WebAssembly — исполнение плагинов у посетителя | единственный способ дать пользователю писать настоящий Python, не отдавая ему сервер |
| **Web Worker** | отдельный поток для плагина | без него зациклившийся плагин вешает вкладку намертво; даёт возможность прервать по таймауту |
| **nh3** | санитизация HTML | пользователь вставляет форматированный текст — без очистки это XSS |
| **Pillow** | обработка изображений: превью, проверка формата | загруженный файл нельзя считать картинкой только по расширению и MIME-типу |
| **argon2-cffi** | хеширование паролей | современный стандарт вместо bcrypt и тем более sha256; устойчив к перебору на видеокартах |
| **pytest** | тесты | в мультиарендном приложении тест «чужую библиотеку не видно» обязателен |
| **Docker + compose** | запуск одной командой | требование почти всех вакансий |
| **ruff** | линтер и форматтер | вытеснил flake8 и black |

### Запасной вариант по версии Python

Остаёмся на **3.14** — он вышел в октябре 2025, за прошедшее время колёса
основных библиотек подтянулись. Но версия всё ещё свежая, и какая-то зависимость
может не поставиться.

Правило на этот случай: **не воевать.** Если что-то не собирается — ставим
**Python 3.13** и идём дальше. Разницы для этого проекта нет никакой, а день,
потраченный на сборку колеса из исходников, не даёт ничего.

### Правило: редактор и HTMX не пересекаются

HTMX подменяет куски страницы, а Editor.js держит своё состояние в этих самых
кусках. Подменил DOM под редактором — редактор превратился в тыкву.

Поэтому граница проводится сразу, а не когда сломается:

- **HTMX** работает на списках, фильтрах, поиске, подгрузке — то есть в режиме
  **просмотра**.
- **Редактор** живёт на отдельном URL как обычная страница. HTMX её не подменяет
  и внутрь неё не лезет. Сохранение — обычным `fetch` в API.

### Решение по базе: почему SQLite сначала, PostgreSQL потом

Начинаем на **SQLite**: файл на диске, ставить нечего, запускается мгновенно.
Переезжаем на **PostgreSQL** на этапе 4, когда понадобится нормальный поиск.

Код при этом почти не меняется — в этом и смысл ORM: SQLAlchemy пишет разный SQL
для разных баз, а твой Python остаётся прежним.

Почему не сразу Postgres: на старте это Docker, конфиги и строки подключения
до того, как появилась первая работающая функция. Первая версия должна запускаться
командой `python main.py`.

Почему в итоге всё-таки Postgres:

- **JSONB** — хранение блоков как JSON с возможностью искать внутри и строить индексы.
  В SQLite JSON есть, но без нормальных индексов.
- **Полнотекстовый поиск** с русской морфологией: «расы» находит «раса».
- **pg_trgm** — поиск с опечатками.
- В вакансиях junior Python backend Postgres требуют, SQLite — нет.

### Почему не MongoDB

Очевидный ответ на «нужна гибкая структура» — документная база. Отвергнут:

- Postgres с JSONB даёт ту же гибкость, **не теряя** связей, транзакций и целостности.
  А связи — половина проекта: статьи ссылаются на статьи, библиотеки на владельцев.
- В Mongo нет внешних ключей: удалил библиотеку — её статьи остались висеть мусором.
- В вакансиях на Python-бэкенд Postgres — норма, Mongo — редкость.

### Чего в проекте не будет

React, Vue, TypeScript, Kubernetes, Kafka, микросервисы, Celery, Redis, Django,
любые LLM. Не потому что плохие, а потому что каждая — это недели, отнятые
у того, что нужно раньше.

### Почему этап 5 нельзя выкинуть

В первой версии этого документа было написано «выкинуть можно 7 и частично 5»
и одновременно «выкинуть нельзя 0, 1, 3, 6, 8». Это противоречие, и его поймал
на ревью друг-тимлид.

Этап 6 стоит на этапе 5 напрямую: у плагина есть автор, плагин принадлежит
библиотеке, включать и выключать его может владелец, а не любой прохожий.
Убрать пользователей и оставить плагины нельзя — не к чему привязывать права.

Поэтому:

- **Обязательный минимум этапа 5:** пользователь, вход и сессии, библиотека
  с владельцем, проверка прав на каждом эндпоинте.
- **Внутри этапа 5 резать можно:** историю правок, публичные и приватные
  библиотеки, часть ролей.
- **Роль модератора платформы не нужна** — вместе с маркетплейсом она ушла
  в Out of Scope (раздел 4).

### Почему этап 7 отложен

Пустой блок — это вложенность: колонки, в которые кладутся другие блоки.
Модель Editor.js в основе **плоская**, и вложенные структуры в ней делаются
отдельной болью, сравнимой по объёму с половиной этапа 3.

Отношение цены к пользе худшее в проекте: много работы, а на собеседовании
про это не спросят. Настройки оформления (7.1–7.2) при желании возвращаются
в этап 3 маленькими кусками, конструктор блоков — нет.

Оценка в 260 часов из первой версии была неправильной — я считал чистое время
человека, который уже умеет. Ты учишься по ходу, и между «знаю, что писать»
и «написал» у новичка коэффициент 2–3.

|---|---|---|---|
| **План А** | ~434 ч чистых (520–570 календарных) | этапы 0–6 и 8 полностью | конец 2027 — начало 2028 |
| **План Б** | ~365 ч (около 440 календарных) | режется интерфейс, не безопасность — см. ниже | до лета 2027 |

**Что режется в плане Б и, главное, что не режется.** Первая версия плана Б
срезала задачи 6.7 и 6.8 — статусы плагина и журнал запусков. Это была ошибка
приоритета: жизненный цикл и аудит — ровно та часть, ради которой весь проект
и затевался как история для собеседования по информационной безопасности.
Резать надо интерфейс, а не модель безопасности.

- **Режем:** блок «связи» мышкой (3.6), автосохранение (3.7), интерфейс типов
  статей (3.8 — типы правятся через Swagger), часть медиа-блоков (3.4),

  трёх (5.5–5.6), ограничение частоты (5.8).
- **Не режем ни в каком варианте:** этап 0 целиком, минимум этапа 5 (5.1–5.4),
  изоляцию плагина (6.2–6.5), статусы и журнал в упрощённом виде (6.7–6.8),

  его придётся показывать запросом к базе — это допустимо, если ты готов такой
  запрос написать и объяснить прямо на собеседовании.

**Как действовать:** идти по плану А, а решение о резке принять **после этапа 0**.
Тогда появится единственная честная цифра — сколько часов реально ушло против
оценки в 42. Она и покажет твой коэффициент.

Порядок этапов в обоих планах одинаковый, и этап 0 одинаковый тоже. Приступать
можно немедленно, ничего не дожидаясь.

## 8. Принципы работы

Взяты из разбора того, почему прошлые попытки обрывались.

1. **Каждая задача заканчивается тем, что видно.** Не «написал слой сервисов»,
   а «запустил и на экране появилась статья».
2. **Код пишет Влад.** Claude Code объясняет, ревьюит, готовит данные — но не пишет
   вместо. Автодополнение целыми блоками (Cursor Tab, Ctrl+K) выключено.
3. **Сначала работает, потом красиво.**
4. **Теория только под текущую задачу.** Курсы «Python с нуля» — та самая ловушка.
5. **Проект переживает паузу.** Задачи зафиксированы заранее, состояние — в журнале.
6. **На ревью приходить пачкой** из 3–5 задач, не после каждой.
